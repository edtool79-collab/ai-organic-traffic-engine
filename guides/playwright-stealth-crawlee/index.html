Choosing the right browser engine in config.json

Different QA targets behave differently depending on TLS signatures, navigator properties, and rendering cost. Traffic Engine AI lets you pick the exact engine per run via engineMode and browserEngine without rewriting scenario steps.

Engine OptionUnderlying StackBest Use Case
patchrightPatched Chromium runtimeDefault high-compatibility browser QA with clean navigator client hints and zero injected webdriver flags

Device profiles & User-Agent Client Hints

src/fingerprintManager.js assigns desktop and mobile weights (desktopChrome, pixel7, iphone14, ipadPro) and keeps Chromium mobile sessions aligned with Android/ARM Client Hints and native deviceScaleFactor instead of leaking mismatched Windows host headers on mobile viewports.

"devices": {
  "desktopChrome": 60,
  "pixel7": 40
},
"stealthMode": "maximum"

Read-only preflight & challenge inspection

Before committing a full run, tools/preflight-target.js classifies target availability (open, cf_interstitial, site_tick, dead), while src/challengeDetector.js detects CAPTCHA or verification walls strictly read-only so workers pause or abort cleanly without attempting to bypass security checks.

For live storefront compatibility audits, verify crawl rules alongside CitedCart AI Robots.txt Checker and CleanTab Lab.

Frequently asked questions

Does Traffic Engine attempt to solve or bypass CAPTCHAs?

No. challengeDetector.js and tools/preflight-target.js are strictly read-only detectors that log and stop cleanly when a challenge interstitial appears.

Can I test both desktop and mobile footprints in one run?

Yes. Configure weights under devices in config.json and run node tests/verify-engine.js chromium to verify navigator integrity.
